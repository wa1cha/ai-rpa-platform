| 版本 | v1（第一版 MVP） |

---

## 1. 项目定位

面向企业电商业务的 **AI + RPA 自动化平台**，解决订单处理中大量重复、机械的人工操作。

系统把「订单获取 → AI 分析 → 任务调度 → RPA 执行 → 结果回传 → 数据记录 → 后台管理」连成闭环，用于证明以下工程能力：

- Python 后端服务设计（FastAPI、分层架构）
- 任务队列与异步编排（Redis）
- AI 在非结构化信息上的应用（LLM 结构化抽取）
- RPA 自动化（浏览器自动化操作真实 UI）
- 数据建模、状态机设计、异常与重试处理
- 容器化与云端部署

**它不是**一个接入真实电商账号、真实 ERP、真实客户数据的生产系统。

## 4. 系统架构

```
                        用户 / 管理员
                              │
                              ↓
                      管理后台 (Vue 3)
                              │
                              ↓
              ┌───────────────────────────────┐
              │        FastAPI 主服务          │
              │ （MySQL / Redis 的唯一出入口）  │
              └──┬────────┬─────────┬─────────┘
                 │        │         │
     ┌───────────┘        │         └────────────┐
     ↓                    ↓                      ↓
   MySQL             Redis 队列              AI Worker
(长期存储)      (task_id + priority)        (异步分析)
                          ↑                      ↓
                          │                   LLM API
                   claim / result
                          ↑
                          │   HTTP only
                    RPA Worker (Playwright)
                          │
                          ↓
                     模拟 ERP (Web)
                   （独立应用 / 独立库）

  关键约束：RPA Worker 只能通过 HTTP 调 FastAPI，
            不直接访问 Redis，也不直接访问 MySQL。
```

### 4.1 关键通信约定（重要）

**Redis 只承载「任务 ID + 优先级」，不承载订单详情。RPA Worker 只与 FastAPI 说话。**

```
FastAPI 生成任务 → 写 MySQL → 把 task_id + priority 推入 Redis ZSET
                                        ↓
RPA Worker 调 FastAPI「POST /rpa/tasks/claim」领取任务
                                        ↓
FastAPI 从 Redis 原子出队最高优先级任务
        → 置 status=RUNNING、写一条 task_executions
        → 返回【完整任务 + 订单数据】
                                        ↓
RPA Worker 用 Playwright 操作模拟 ERP 界面
                                        ↓
RPA Worker 调 FastAPI「POST /rpa/tasks/{id}/result」回传结果
                                        ↓
FastAPI 更新任务与订单状态 → 写 MySQL
```

**这样设计的理由：**
- RPA 端**完全不碰 Redis、也不碰 MySQL**，只认 HTTP 接口，职责最干净
- 出队、鉴权、状态变更全部集中在 FastAPI 一处，逻辑单点，便于排查与审计
- RPA Worker 跑在另一台机器（Windows），权限最小化：它的 JWT 只能访问 `/rpa/*`
- 以后把 Redis 换成 RabbitMQ / Kafka，**RPA 代码零改动**

**配套机制：僵尸任务回收。** Worker 领取任务后每 30 秒调 `POST /rpa/tasks/{id}/heartbeat`；若某任务超过 5 分钟无心跳，定时任务将其判为僵尸，重新入队或置 `FAILED`。不处理的话，Worker 一旦崩溃，任务会永远卡在 `RUNNING`。详见《数据库设计》§6.1。

### 4.2 AI 分析异步化（重要）

订单导入接口**不**同步调用 LLM。100 单/分钟下同步调用会直接阻塞导入。

```
导入订单 → 写 MySQL → 推入「待分析」队列
                            ↓
                    AI Worker 消费
                            ↓
                    写 ai_analyses 表
                            ↓
                    硬规则合并 → 生成 RPA 任务
```

即引入**两类 Worker**：`AI Worker`（分析）和 `RPA Worker`（执行）。

### 4.3 模拟 ERP 的特殊约束

模拟 ERP 自己有后端 API（RPA 操作页面时，页面会调这些 API 存数据）。

但是 —— **RPA 明令禁止直接调用这些 API 完成业务操作**。RPA 必须通过浏览器真实操作页面元素。

这是刻意设计，理由：
- 否则「RPA」退化成普通 HTTP 客户端，项目失去 RPA 的展示价值
- 真实企业场景中，老 ERP 往往没有 API，只能靠界面操作
- 面试可回答：「为什么不直接调 API 而要用 RPA？」

## 5. 核心业务流程（v1 闭环）

```
① 模拟平台生成订单 Excel
        ↓
② 管理员在后台导入 Excel
        ↓
③ FastAPI 校验并写入 MySQL（orders）
        ↓
④ 订单进入「待分析」队列
        ↓
⑤ AI Worker 分析订单文本 → 写 ai_analyses
        ↓
⑥ 硬规则引擎 + AI 结果合并 → 得出最终判定
        ↓
⑦ 生成 RPA 任务（tasks）
     ├─ 无异常 → PENDING
     └─ 有异常 → WAITING_REVIEW（等人工审核）
        ↓
⑧ 任务 ID + 优先级推入 Redis 队列
        ↓
⑨ RPA Worker 按优先级取任务
        ↓
⑩ 调 FastAPI 拉订单详情
        ↓
⑪ Playwright 操作模拟 ERP（登录→订单管理→新建→填写→保存→提交审核）
        ↓
⑫ 回传执行结果（成功/失败/截图/错误信息）
        ↓
⑬ FastAPI 更新任务状态、写执行日志
        ↓
⑭ 失败则重试（≤3 次），超限转 FAILED → 人工处理
        ↓
⑮ 管理后台展示全部数据
```

## 7. 模块职责

### 7.1 Backend（FastAPI 主服务）

- 接收 HTTP 请求，提供 REST API 给前端、AI Worker、RPA Worker
- 订单管理与导入
- AI 分析结果管理与人工修正
- 任务生成、状态流转、调度
- 提供 RPA 领取任务、心跳、回传结果的接口（`/api/v1/rpa/*`）
- 操作 MySQL，推送任务到 Redis
- 统一异常处理、日志、鉴权

**分层**：`api → services → repositories → models`，`core` 放配置/日志，`workers` 放后台任务。

### 7.2 MySQL

长期数据仓库，保存用户、订单、AI 结果、任务、执行记录、修正记录。所有状态流转以 MySQL 为准。

### 7.3 Redis

- 任务队列（含优先级，ZSET）
- 短期状态 / 去重
- 让订单处理与 RPA 执行解耦

**由 FastAPI 独占访问，RPA Worker 不直连。**

### 7.4 AI Worker

消费「待分析」队列，调用 `AIClient`，把非结构化文本转成结构化 JSON，写入 `ai_analyses`。

### 7.5 硬规则引擎

放在 FastAPI 内部（v1 硬编码，不做规则配置化）。负责 AI 处理不了的确定性判断。

### 7.6 RPA Worker

Python + Playwright。调 FastAPI `POST /rpa/tasks/claim` 领取任务（一次性拿到完整任务 + 订单数据）→ 操作模拟 ERP 界面 → 调 FastAPI 回传结果。

**不直接访问 Redis，也不直接访问 MySQL**，只走 HTTP 接口。执行期间每 30 秒发一次心跳。

### 7.7 模拟 ERP

独立 Web 应用（独立库 `mock_erp`），包含：登录、工作台、订单列表、新建订单、订单详情、订单审核、库存查询。供 RPA 操作。

自己的 `/api/*` 只服务于页面，**不供 RPA 直接调用**（通过 `X-ERP-UI` 请求头做技术校验，见《模拟ERP设计》§5.1）。

**v1 不含出库管理**（§2.2 已明确不做真实出库）。详细页面设计与选择器规范见《模拟ERP设计》。

### 7.8 模拟电商平台

v1 极简：一个生成模拟订单 Excel 的脚本，不做成 web 应用。

### 7.9 管理后台（Vue 3）

- Dashboard：订单数量、待处理/执行中/成功/失败任务、AI 异常订单
- 订单列表
- 任务列表
- RPA 执行日志
- AI 分析结果查看
- 人工复核 / AI 结果修正
- 手动重试

## 8. 业务规则

### 8.1 硬规则 与 AI 的分工

**原则：硬规则优先，AI 只负责理解复杂自然语言。**

```
硬规则（确定性）
      ↓
AI 分析（非确定性，处理自然语言）
      ↓
合并 → 最终判定
```

硬规则示例（v1 硬编码）：

| 规则 | 结果 |
| --- | --- |
| 金额 > 10000 | 强制进入人工审核 |
| 地址字段缺失/过短 | `risk_level = HIGH`，标记异常 |
| 客户在黑名单 | 直接标记异常 |
| 数量 ≤ 0 或金额异常 | 标记异常 |

AI 负责的部分（示例）：

| 输入 | 期望输出 |
| --- | --- |
| "客户说孩子明天生日，希望今天发货" | `priority=HIGH, deadline=TODAY` |
| "不要发顺丰，请发中通" | `risk_level=MEDIUM, risk_reason=物流方式与默认冲突` |
| "如果不能发货请联系我" | `need_contact=true` |

**冲突处理**：硬规则与 AI 结果冲突时，**以硬规则为准**，并把冲突记录进日志。

### 8.2 异常订单定义（触发人工审核）

1. 地址信息不完整
2. AI 判断需要人工联系客户
3. 商品库存不足
4. 高金额订单（> 10000）
5. 买家留言与订单信息冲突（如指定物流与默认不符）
6. 黑名单客户

命中任一条 → 任务进入 `WAITING_REVIEW`，RPA 不会取。

### 8.3 重试策略

```
第 1 次执行失败 → 自动重试
第 2 次执行失败 → 自动重试
第 3 次执行失败 → 任务 FAILED → 人工处理
```

- 最大重试次数：**3**
- 每次执行都写一条 `task_executions` 记录
- 必须记录：失败原因、错误截图、失败时间、重试次数

### 8.4 任务优先级

`HIGH` > `MEDIUM` > `LOW`。

Redis 队列必须支持优先出队，例如：

```
LOW, LOW, HIGH, LOW   →   RPA 优先取 HIGH
```

**注意**：Phase 3 建队列时就要把 `priority` 字段和优先出队逻辑预留好，AI 后续接入只负责填这个字段，避免返工。

## 9. 任务状态机

```
                        订单导入
                           ↓
                      AI 分析（异步）
                           ↓
                        生成任务
                     ┌─────┴─────┐
              无异常 │           │ 有异常
                     ↓           ↓
                  PENDING   WAITING_REVIEW
                     │           │
                     │      ┌────┴────┐
                     │  审核通过   审核驳回
                     │      │        ↓
                     │      │    CANCELLED
                     ↓      ↓
                    QUEUED（入 Redis，按优先级）
                       ↓
                    RUNNING
                       ↓
                  ┌────┴────┐
              成功 │         │ 失败
                  ↓         ↓
              SUCCESS   retry_count < 3 ?
                            ├─ 是 → 重新入队 → QUEUED
                            └─ 否 → FAILED → 人工处理
```

**状态枚举**：`PENDING` / `WAITING_REVIEW` / `QUEUED` / `RUNNING` / `SUCCESS` / `FAILED` / `CANCELLED`

**设计要点**：所有任务共用一张 `tasks` 表，用状态区分流程分支，而不是拆成多张表。逻辑更简单，后台也更好统一展示。

## 12. 关键设计决策（面试必答）

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 FastAPI？ | 异步支持好、类型校验（Pydantic）、自动生成 API 文档、适合 IO 密集的调度类服务 |
| 为什么用 Redis 做队列？ | 订单处理与 RPA 执行解耦；RPA 执行慢且不可控，不能让 FastAPI 同步等待；支持优先级 |
| 为什么 RPA 不直连数据库？ | 职责隔离。RPA 只负责操作 UI，数据一致性由 FastAPI 单点保证 |
| 为什么 RPA 也不直连 Redis？ | 出队/鉴权/状态变更集中在 FastAPI 一处，逻辑单点；RPA 端不用引入 redis 客户端、不懂队列协议 |
| Redis 里为什么不存订单详情？ | 避免数据多份拷贝不一致；队列只做「有活干」的信号；换队列中间件时 RPA 代码不用改 |
| Worker 领了任务后崩溃怎么办？ | 心跳 + 定时扫描回收僵尸任务（`heartbeat_at` 超 5 分钟），否则任务永远卡在 RUNNING |
| 为什么给 RPA 单独的角色和接口组？ | Worker 跑在另一台机器，权限最小化，它的 JWT 只能访问 `/rpa/*` |
| 为什么 RPA 不调 ERP 的 API？ | 真实老 ERP 常无 API；且直接调 API 就不是 RPA 了 |
| AI 和硬规则怎么配合？ | 硬规则处理确定性判断，AI 处理自然语言；冲突时硬规则优先并记录日志 |
| 为什么 AI 分析要异步？ | 100 单/分钟同步调 LLM 会阻塞导入接口；异步后导入与分析解耦 |
| RPA 失败怎么重试？ | 每次执行独立记录，最多 3 次，超限转 FAILED 交人工，保留错误截图便于排查 |
| 任务状态怎么流转？ | 见第 9 章状态机；单表 + 状态字段，而不是拆表 |
| MySQL 存什么？ | 订单、AI 结果、任务、执行记录、修正记录 —— 长期可追溯数据 |
| 为什么要 Docker？ | 环境一致性；一键拉起后端/MySQL/Redis；便于部署到云服务器 |
