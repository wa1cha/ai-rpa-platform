## 1. 前置条件

| 组件 | 说明 |
| --- | --- |
| Python 3.12 | 需要装好三套依赖：主平台 `backend/requirements.txt`、模拟 ERP `mock/erp/requirements.txt`、RPA Worker `rpa/requirements.txt` |
| MySQL 9.x | 本机（brew 装的也行）。**root 无密码是可以的** —— `init_db.sh` 支持直接回车 |

## 2. 一次性初始化

```bash
# ① 配置
cp .env.example .env
#   按注释填好 MySQL / Redis / JWT_SECRET / ADMIN_PASSWORD / WORKER_PASSWORD /
#   MOCK_ERP_* 等。PYTHON_BIN 指向装好依赖的解释器。

# ② 建库 + 建表 + 建应用账号（幂等，可重复跑）
MYSQL_ROOT_PASSWORD= ./scripts/init_db.sh

# ③ 创建管理员账号与 RPA Worker 账号（口令读自 .env；幂等）
python scripts/seed_admin.py
python scripts/seed_worker.py
python scripts/seed_blacklist.py   # 种一条示例黑名单手机号（幂等，表非空则跳过）

# ④ 装 Chromium（只需一次）
python -m playwright install chromium

# ⑤ 把 ai/ 装成「可编辑安装」的包（只需一次）
#    AI 分析代码刻意独立于 backend，backend 以规范包方式 `import ai`
#    —— 所以要先把它装进解释器，而不是去改 sys.path。
pip install -e ai/
```

> **关于 `ai/`**：它是独立的发行包 `ai-rpa-analysis`（import 名仍是 `ai`），
> 与 `backend/` 之间是**单向依赖**（backend → ai，反过来不允许）。
> 装好后任意目录下 `python -c "import ai"` 都能通过。
> 要跑 AI 分析得在 `.env` 里填 `AI_API_KEY`；留空时 `ai_worker` 每轮空转
> （订单停在 `IMPORTED`、不报错，也不崩作业循环）—— 本地不想花 API 费时就这么留着。

`init_db.sh` 做两件事：

1. 建两个库 `ai_rpa`（主库）与 `mock_erp`（模拟 ERP 库），并建应用账号、只授权这两个库。
2. 载入 `database/schema/0*.sql` 建表：`001..008` 与 `010` → 主库，`009_mock_erp` → 模拟 ERP 库。

> 表结构以 `database/schema/` 下的文件为准 —— 它们已包含历次迁移的最终形态
> （例如 `005` 已带 `cancel_reason`、`009` 已带 ERP 来源单号唯一键、`010` 是客户黑名单）。
> `database/migrations/` 里的 `010/011/012` 是给**已经建过表的旧库**做增量升级的，全新初始化不用再跑。
>
> 建表用的是 `CREATE TABLE IF NOT EXISTS`：重复执行不会破坏已有数据，
> 但也**不会**帮你升级已存在的旧表结构。

**root 认证**：`init_db.sh` 优先读环境变量 `MYSQL_ROOT_PASSWORD`（可以是**空串**，表示无密码）；
没设时才隐藏式提示输入。本地 brew 装的 MySQL root 通常无密码，直接回车即可。

## 3. 四个进程

系统由**四个独立进程**组成，各有各的日志与 pid 文件：

| # | 进程 | 启动脚本 | 端口 | 日志 | pid |
| --- | --- | --- | --- | --- | --- |
| ① | 主平台 backend | `./scripts/start.sh` | `8000` | `logs/backend.log` | `logs/backend.pid` |
| ② | 作业进程（僵尸回收 + AI 补偿 + AI 分析） | `./scripts/start_workers.sh` | 无 | `logs/workers.log` | `logs/workers.pid` |
| ③ | 模拟 ERP | `./scripts/start_mock_erp.sh` | `8001` | `logs/mock_erp.log` | `logs/mock_erp.pid` |
| ④ | RPA Worker | `./scripts/run_rpa_worker.sh` | 无 | `logs/rpa_worker.log` | `logs/rpa_worker.pid` |

### 3.1 启动顺序

主平台要先起来：Worker 启动时会**先登录主平台再开浏览器**，连不上会立刻失败退出。
其余三个之间没有严格先后。

```bash
./scripts/start.sh            # ① 主平台
./scripts/start_workers.sh    # ② 僵尸回收
./scripts/start_mock_erp.sh   # ③ 模拟 ERP
./scripts/run_rpa_worker.sh   # ④ RPA Worker（后台）

# 想看着它点浏览器（演示用）：
./scripts/run_rpa_worker.sh --foreground --headed
# 只想让它跑一笔就退：
./scripts/run_rpa_worker.sh --foreground --once
```

每个脚本都支持 `--foreground`（前台跑、Ctrl-C 停，调试用）。
`start.sh` 与 `start_workers.sh` 会**拒绝重复启动**，避免两个进程抢端口/抢任务。

### 3.2 停止

```bash
./scripts/stop.sh     # 一次按顺序停掉上面四个
```

先 `SIGTERM` 给它们机会优雅退出（关连接池、关浏览器），10 秒不走才 `SIGKILL`。
四个一起停是刻意的 —— 喊「停」的时候想要的是「这套东西别跑了」。

## 4. 配置

全部配置集中在根目录 `.env`（样例见 `.env.example`），按用途分组的完整清单见
[`README.md`](../README.md#配置)。几个容易踩的点：

- **`PYTHON_BIN`**：必须指向装好依赖的**绝对路径**。起停脚本都读它，脚本里不写死机器路径。
- **`RPA_API_BASE_URL` 留空即可**：Worker 会按 `APP_HOST`/`APP_PORT` 推导出
  `http://127.0.0.1:8000/api/v1`。Worker 跑在**另一台机器**上时才需要显式填主平台地址。
- **`MOCK_ERP_PAGE_DELAY_MS`**：模拟 ERP 每次 HTML 跳转刻意变慢（默认 1500ms），
  逼 RPA 用「等待元素」而不是「固定 sleep」——故意留的坑，别调成 0。
- **`MOCK_ERP_FAIL_RATE`**：故障注入开关（`0`~`1`）。设成 `1.0` 可复现「重试耗尽 → 转人工」，
  验证完记得改回 `0`。临时验证也可以不改 `.env`，用进程环境变量覆盖（见 §7.5）。

## 7. 常见问题排查

### 7.1 `解释器不存在或不可执行`

`.env` 里的 `PYTHON_BIN` 没填或填错。填成装了依赖的那个解释器的**绝对路径**。

### 7.2 端口被占用

`start.sh` / `start_mock_erp.sh` 启动时会探健康检查，端口被占会直接报错并打印日志末尾。
先 `./scripts/stop.sh`；若还有残留进程，用 `lsof -i :8000` / `lsof -i :8001` 找出来。

### 7.3 MySQL root 认证失败

- **不要**用 `-p` 配合管道喂密码：root 无密码时 `-p` 反而被 MySQL 拒
  （「发一个空密码」和「不发密码」在 MySQL 眼里不是一回事）。脚本已改用 `MYSQL_PWD`。
- 想完全不交互（CI / 无 TTY）：`MYSQL_ROOT_PASSWORD= ./scripts/init_db.sh`
  —— 注意是**设为空串**而不是「不设」，两者在脚本里走的是不同分支。

### 7.4 RPA Worker 起来了又退出

Worker 启动时**先登录主平台、再开浏览器**，平台连不上或口令不对会立刻失败。
看 `logs/rpa_worker.log`：后台脚本的启动探针 grep 的是 `RPA Worker 启动完成，开始领任务`
这一行，它打在**登录成功 + 浏览器开起来之后** —— 探针没命中就是没真正就绪。

### 7.5 想复现「重试耗尽 → 转人工」

不必改 `.env`，用进程环境变量覆盖即可（pydantic-settings 里真实环境变量优先于 `.env`）：

```bash
MOCK_ERP_FAIL_RATE=1.0 ./scripts/start_mock_erp.sh
# 跑 4 次 Worker，期望 4 条 execution 全 FAILED、任务终态 FAILED、订单 FAILED、有一条 TASK_FAILED 通知
./scripts/stop.sh && ./scripts/start_mock_erp.sh   # 改回正常
```

### 7.6 e2e 测试超时

`rpa/tests -m e2e` 的前置是：主平台 + 模拟 ERP 都活着、装了 Chromium，
**且队列里除了刚 seed 的那一笔没有别的待办**。Worker 是 FIFO 领任务、不带过滤条件，
队列里堆着别的任务时它会先干那些，测试最后拿到一个含义不明的超时。
服务没起时 e2e 是 **skip 而不是 fail**（刻意的：忘了起服务不该看起来像代码坏了）。

## 9. Docker Compose 一键部署（Phase 7，本机）

不必按 §3 一个个起进程 —— 装了 Docker Desktop 后，compose 把 8 个服务一次拉齐，
在容器网络里跑通完整链路：Frontend → Backend → MySQL/Redis → AI Worker →
RPA Worker → Mock ERP → 结果回写。

### 9.1 起停

```bash
cp .env.example .env       # 首次；填好 MYSQL_ROOT_PASSWORD 等（见 9.4）
./scripts/deploy.sh up     # = docker compose up -d --build（首次必须 --build）
./scripts/deploy.sh ps     # 看各服务状态
./scripts/deploy.sh logs   # 跟踪日志
./scripts/deploy.sh down   # 停（保留数据卷）
./scripts/deploy.sh reset  # 停并清空数据卷（下次重新初始化 + 灌种子）
```

访问 **http://localhost:8080**（唯一对外端口），用 `.env` 里的管理员账号登录。

### 9.2 与 bare-metal 的差异

| | bare-metal（§2 起） | Docker（本节） |
| --- | --- | --- |
| MySQL / Redis | 宿主机 brew | 容器（`mysql:8.4` / `redis:7-alpine`） |
| 账号 / 种子 | 手动跑 `seed_*.py` | `seed` 一次性服务自动跑 |
| 前端 | Vite dev（5173） | nginx 托管构建产物 + 反代 `/api`（8080） |
| 地址 | `127.0.0.1` | 容器内服务名（`mysql`/`redis`/`backend`/`mock-erp`） |
| `ai` 包 | `pip install -e ai/` | 镜像内普通安装（COPY + pip install） |

### 9.3 MySQL 初始化

容器首次启动（数据卷为空）时，`docker/mysql-init/10-init.sh` 复刻 `init_db.sh` 的逻辑：
建 `mock_erp` 库并授权、逐文件改写 `USE` 载入 schema、载入模拟 ERP 库存种子。
数据卷非空时不重跑 —— 想重新初始化先 `./scripts/deploy.sh reset`。

### 9.4 所需的 `.env` 项

compose 从 `.env` 读配置（`env_file`）。其中 **`MYSQL_ROOT_PASSWORD` 必填** ——
bare-metal 用不到它，Docker 缺了会直接报错；`.env.example` 已带占位值。
`AI_API_KEY` 填了才会真调 LLM 分析；留空则 AI Worker 空转，订单停在 `IMPORTED`。

### 9.5 排障

- **首次 `up` 没带 `--build`**：镜像不存在会起不来。用 `--build`，或先 `./scripts/deploy.sh build`。
- **只有前端对外**：要 curl 后端就进容器 —— `docker compose exec backend python -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8000/api/v1/health').read())"`。
- **RPA Worker 报「找不到浏览器」**：基镜像标签与 playwright 版本要对得上。
  `rpa/Dockerfile` 已把 requirements 里的 playwright 行滤掉，用镜像自带的版本。

## 10. 云服务器部署（Phase 7，腾讯云，已完成）

2026-10-08 部署并全链路验证：**腾讯云 Ubuntu 24.04 / x86_64 / 2 核 2G**，
公网可访问（地址与口令见本机 `.env` 的 `CLOUD_` 段，不写入仓库）。
形态是**裸 IP 演示** —— 无域名、无 HTTPS，安全组只放行 8080；其余服务（backend:8000、
mock-erp:8001、MySQL、Redis）都只在 compose 内网，不对外。

### 10.1 步骤

```bash
# ① 服务器装 docker engine + compose v2 插件（2.40.3 验证通过）
# ② 把源码放到 /opt/ai-rpa-platform
# ③ 按 §10.3 写服务器 .env
cd /opt/ai-rpa-platform
docker compose up -d --build      # ④ 构建并起全套（首次必须 --build）
# ⑤ 云控制台安全组放行 TCP 8080
```

### 10.2 两个必须知道的坑

**a. 架构不同，只能在服务器上构建。** 本机 Mac 是 arm64，云服务器 x86_64 ——
镜像体系不通，**不能把本机镜像推上去**，只能送源码过去现构建。

**b. 国内拉镜像极慢，靠镜像源提速。** `mcr.microsoft.com` 的 playwright 官方镜像层
实测 ~78 KiB/s（2GB 要拉几小时），已弃用。现在：

- `rpa/Dockerfile` 基镜像改为 **`python:3.12-slim-bookworm`** + 浏览器从
  `playwright.azureedge.net` 拉（实测 **12.7 MB/s**）。
- 四个 `Dockerfile` 的镜像源都做成**构建参数**（`ARG APT_MIRROR` / `PIP_INDEX_URL` /
  `PIP_TRUSTED_HOST` / `NPM_REGISTRY`），**默认留空 = 走官方源**，所以本机 / 海外构建
  完全不受影响；云上由 compose 从服务器 `.env` 透传内网源。
- 云上提速靠服务器 `.env` 里那四项腾讯云**内网**源（`mirrors.tencentyun.com`）——
  内网源只有腾讯云机器可达，**故意不进 git**，否则本机构建会直接失败。
- 基镜像**必须是 bookworm、不能是 trixie**：playwright 1.49 的 `install --with-deps`
  依赖清单按 Debian 12 写，trixie 上 `ttf-unifont` 等包名已改，apt 会直接失败。

### 10.3 云上 `.env` 与凭据

- 服务器 `/opt/ai-rpa-platform/.env` 与 `.env.example` 同构，额外填了 §10.2 的镜像源四项。
- 云上的独立口令（MySQL / ADMIN / WORKER / JWT）**另存一份在本机 `.env` 末尾**
  （`CLOUD_` 前缀），**绝不进 git**。
- 已把本机 `~/.ssh/id_ed25519.pub` 装到服务器 root，重部署免密：
  `ssh root@$CLOUD_SERVER_IP 'cd /opt/ai-rpa-platform && docker compose up -d --build'`。

### 10.4 注意

- 服务器上另有一个**用户自己的 mysql57 容器占着 3306 —— 别动**。
  compose 的 mysql / redis 只走容器内部网络，不映射到宿主机，两者不冲突。
- 服务器源码已与 git 同步；改完代码重部署时，把改动同步到 `/opt/ai-rpa-platform`
  后再 `docker compose up -d --build`。
