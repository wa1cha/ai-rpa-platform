# AI-RPA 电商订单智能自动化平台 — 数据库设计 v1

> 配套文档：`docs/需求规格.md`（需求来源）、`docs/API接口设计.md`（接口定义）
> 数据库：MySQL 8.0+　引擎：InnoDB　字符集：`utf8mb4` / `utf8mb4_unicode_ci`

---

## 1. 设计约定

| 项 | 约定 |
| --- | --- |
| 库名 | `ai_rpa`（主库）；模拟 ERP 使用**独立的库** `mock_erp` |
| 表名 | 小写 + 下划线 + **复数**（`orders`、`tasks`） |
| 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT` |
| 外键 | 命名 `fk_<表>_<引用>` |
| 唯一键 | 命名 `uk_<表>_<字段>` |
| 普通索引 | 命名 `idx_<表>_<字段>` |
| 时间 | 统一 `DATETIME`，`created_at` / `updated_at` 自动维护 |
| 金额 | `DECIMAL(12,2)`，**绝不用 FLOAT/DOUBLE** |
| 布尔 | `TINYINT(1)`，0/1 |
| 枚举 | 用 `VARCHAR` 存字符串，**不用 MySQL `ENUM` 类型** |
| 软删除 | v1 不做，需要时再加 `deleted_at` |
| 时区 | 库统一 `+08:00`，应用层不存时区 |

### 1.1 为什么枚举用 VARCHAR 而不是 ENUM

`ENUM` 改动值域要 `ALTER TABLE`，且 App 层拿到的语义不直观、跨语言映射麻烦。用 `VARCHAR` + 应用层校验（Python `Enum`），扩展只需改代码。代价是丢失数据库层约束，靠 Pydantic 校验补上。

### 1.2 为什么不用软删除

v1 的业务数据（订单、任务、执行记录）都是**审计性质**的，本来就不该删。`CANCELLED` 用状态字段表达，不需要软删除。

## 2. 实体关系

```
                    ┌──────────┐
                    │  users   │
                    └────┬─────┘
                         │ reviewed_by
                         │ uploaded_by
                         ↓
┌────────────────┐    ┌──────────────┐
│ import_batches │───→│    orders    │
└────────────────┘    └──────┬───────┘
                             │ 1
                             │
                    ┌────────┴────────┐
                    │ N               │ N
                    ↓                 ↓
            ┌───────────────┐  ┌─────────────┐
            │ ai_analyses   │  │    tasks    │
            └───────┬───────┘  └──────┬──────┘
                    │ 1               │ 1
                    │                 │
                    └──→ ai_review_logs│ N
                                       ↓
                              ┌──────────────────┐
                              │ task_executions  │
                              └──────────────────┘

        notifications ──(弱关联)──→ orders / tasks
```

**关系说明**

| 关系 | 基数 | 说明 |
| --- | --- | --- |
| `import_batches` → `orders` | 1 : N | 一次 Excel 导入产生多笔订单 |
| `orders` → `ai_analyses` | 1 : N | 支持重新分析，取 `created_at` 最新一条为有效结果 |
| `orders` → `tasks` | **1 : 1** | v1 一个订单对应一个任务，用**唯一索引**强制 |
| `tasks` → `task_executions` | 1 : N | 每次执行（含每次重试）一条记录 |
| `ai_analyses` → `ai_review_logs` | 1 : N | 一次分析结果可被人工修正多个字段 |

## 4. 建表语句

### 4.1 `users` — 用户

```sql
CREATE TABLE users (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  username       VARCHAR(50)     NOT NULL                COMMENT '登录名',
  password_hash  VARCHAR(255)    NOT NULL                COMMENT 'bcrypt 哈希，绝不存明文',
  role           VARCHAR(20)     NOT NULL DEFAULT 'ADMIN' COMMENT 'ADMIN/WORKER，取值见 core/enums.py',
  is_active      TINYINT(1)      NOT NULL DEFAULT 1      COMMENT '1启用 0禁用',
  last_login_at  DATETIME        NULL                    COMMENT '最后登录时间',
  created_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_users_username (username)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户';
```

### 4.2 `import_batches` — 导入批次

每次上传 Excel 生成一条，用于回答「部分行导入失败怎么办」——**全部成功才提交，有失败行则整批回滚并把失败原因记在这里**。

```sql
CREATE TABLE import_batches (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  filename      VARCHAR(255)    NOT NULL              COMMENT '原始文件名',
  uploaded_by   BIGINT UNSIGNED NULL                  COMMENT '上传人',
  total_rows    INT             NOT NULL DEFAULT 0    COMMENT 'Excel 总行数',
  success_rows  INT             NOT NULL DEFAULT 0    COMMENT '成功导入行数',
  failed_rows   INT             NOT NULL DEFAULT 0    COMMENT '失败行数',
  status        VARCHAR(20)     NOT NULL DEFAULT 'PROCESSING'
                                COMMENT 'PROCESSING/COMPLETED/FAILED',
  error_detail  JSON            NULL                  COMMENT '[{"row":3,"order_no":"..","reason":"手机号格式错误"}]',
  created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  finished_at   DATETIME        NULL,
  PRIMARY KEY (id),
  KEY idx_import_batches_status (status),
  KEY idx_import_batches_created_at (created_at),
  CONSTRAINT fk_import_batches_user FOREIGN KEY (uploaded_by)
    REFERENCES users (id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='导入批次';
```

### 4.3 `orders` — 订单

```sql
CREATE TABLE orders (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_no       VARCHAR(64)     NOT NULL              COMMENT '订单号，业务唯一',
  platform       VARCHAR(32)     NOT NULL DEFAULT 'mock' COMMENT '来源平台，v1 固定 mock',
  ordered_at     DATETIME        NOT NULL              COMMENT '下单时间（业务时间）',
  customer_name  VARCHAR(64)     NOT NULL,
  phone          VARCHAR(32)     NOT NULL,
  address        VARCHAR(512)    NOT NULL              COMMENT '收货地址',
  product_name   VARCHAR(255)    NOT NULL,
  sku            VARCHAR(64)     NOT NULL,
  quantity       INT             NOT NULL DEFAULT 1,
  amount         DECIMAL(12,2)   NOT NULL              COMMENT '订单金额',
  buyer_message  VARCHAR(1000)   NULL                  COMMENT '买家留言（AI 主要输入）',
  seller_note    VARCHAR(1000)   NULL                  COMMENT '卖家备注',
  status         VARCHAR(20)     NOT NULL DEFAULT 'IMPORTED'
                                 COMMENT 'IMPORTED/ANALYZING/ANALYZED/TASK_CREATED/COMPLETED/FAILED',
  import_batch_id BIGINT UNSIGNED NULL                 COMMENT '来源导入批次',
  imported_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '导入时间',
  created_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_orders_order_no (order_no),
  KEY idx_orders_status (status),
  KEY idx_orders_imported_at (imported_at),
  KEY idx_orders_ordered_at (ordered_at),
  KEY idx_orders_batch (import_batch_id),
  CONSTRAINT fk_orders_batch FOREIGN KEY (import_batch_id)
    REFERENCES import_batches (id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='订单';
```

> **命名说明**：需求规格里这个字段叫 `created_at`（下单时间）。为避免与「行创建时间」混淆，此处改名为 `ordered_at`，含义不变。

### 4.4 `ai_analyses` — AI 分析结果

```sql
CREATE TABLE ai_analyses (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_id       BIGINT UNSIGNED NOT NULL,
  priority       VARCHAR(16)     NULL              COMMENT 'LOW/MEDIUM/HIGH',
  deadline       VARCHAR(32)     NULL              COMMENT 'TODAY/TOMORROW/NONE/具体日期',
  need_contact   TINYINT(1)      NULL              COMMENT '是否需要联系客户',
  risk_level     VARCHAR(16)     NULL              COMMENT 'LOW/MEDIUM/HIGH',
  risk_reason    VARCHAR(500)    NULL              COMMENT '风险原因（自然语言）',
  action         VARCHAR(500)    NULL              COMMENT '建议动作（自然语言）',
  model_name     VARCHAR(64)     NULL              COMMENT '如 deepseek-chat',
  prompt_version VARCHAR(32)     NULL              COMMENT 'Prompt 版本，便于回溯效果',
  raw_response   JSON            NULL              COMMENT 'LLM 原始返回，排查用',
  status         VARCHAR(16)     NOT NULL DEFAULT 'SUCCESS' COMMENT 'SUCCESS/FAILED',
  error_message  VARCHAR(500)    NULL              COMMENT 'AI 调用失败原因',
  duration_ms    INT             NULL              COMMENT 'AI 调用耗时',
  created_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_ai_analyses_order (order_id, created_at),
  KEY idx_ai_analyses_risk (risk_level),
  CONSTRAINT fk_ai_analyses_order FOREIGN KEY (order_id)
    REFERENCES orders (id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='AI分析结果';
```

> `status='FAILED'` 的行允许业务字段为 NULL —— AI 调用失败也要留痕，否则「订单卡在 ANALYZING」无从排查。

### 4.5 `tasks` — RPA 任务

```sql
CREATE TABLE tasks (
  id               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_id         BIGINT UNSIGNED NOT NULL,
  ai_analysis_id   BIGINT UNSIGNED NULL              COMMENT '生成时的依据，便于追溯「为什么是HIGH」',
  priority         VARCHAR(16)     NOT NULL DEFAULT 'MEDIUM'
                                   COMMENT 'LOW/MEDIUM/HIGH，决定出队顺序',
  status           VARCHAR(20)     NOT NULL DEFAULT 'PENDING'
                                   COMMENT 'PENDING/WAITING_REVIEW/QUEUED/RUNNING/SUCCESS/FAILED/CANCELLED',
  need_review      TINYINT(1)      NOT NULL DEFAULT 0 COMMENT '是否需人工审核',
  review_result    VARCHAR(16)     NULL               COMMENT 'APPROVED/REJECTED',
  review_reason    VARCHAR(500)    NULL               COMMENT '审核意见',
  cancel_reason    VARCHAR(500)    NULL               COMMENT '取消 / 人工处置说明，与 review_reason 分开',
  reviewed_by      BIGINT UNSIGNED NULL,
  reviewed_at      DATETIME        NULL,
  retry_count      INT             NOT NULL DEFAULT 0 COMMENT '已重试次数',
  max_retry        INT             NOT NULL DEFAULT 3 COMMENT '最大重试次数',
  last_error       VARCHAR(1000)   NULL               COMMENT '最近一次失败原因（冗余，列表页直接用）',
  queued_at        DATETIME        NULL               COMMENT '进入队列时间',
  claimed_by       VARCHAR(64)     NULL               COMMENT '领取任务的 Worker 标识',
  heartbeat_at     DATETIME        NULL               COMMENT '最近心跳，用于回收僵尸任务',
  finished_at      DATETIME        NULL               COMMENT '终态时间',
  created_at       DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at       DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tasks_order (order_id)                COMMENT '强制 1订单=1任务',
  KEY idx_tasks_status_priority (status, priority, created_at)
                                   COMMENT 'claim 出队与列表筛选的主力索引',
  KEY idx_tasks_status (status),
  KEY idx_tasks_created_at (created_at),
  CONSTRAINT fk_tasks_order FOREIGN KEY (order_id)
    REFERENCES orders (id) ON DELETE CASCADE,
  CONSTRAINT fk_tasks_ai_analysis FOREIGN KEY (ai_analysis_id)
    REFERENCES ai_analyses (id) ON DELETE SET NULL,
  CONSTRAINT fk_tasks_reviewer FOREIGN KEY (reviewed_by)
    REFERENCES users (id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='RPA任务';
```

> **`uk_tasks_order` 是把业务规则写进数据库**：v1「一订单 = 一任务」不靠代码自觉，靠唯一索引兜底。以后要支持一单多任务（如分批发货），得先显式去掉这个索引——这是个提醒点，不会被悄悄破坏。

> **`cancel_reason` 为什么不复用 `review_reason`**：后者是审核意见。复用会让
> 「`status=CANCELLED` 但 `review_result` 为 NULL、`review_reason` 有值」这种行出现，
> 读数据的人只能靠猜这行是审核结论还是取消原因。两件事分开存，查询时不用带上下文。
> 已建过的库用 `database/migrations/010_add_cancel_reason.sql` 补列（幂等）。

### 4.7 `ai_review_logs` — AI 结果人工修正记录

```sql
CREATE TABLE ai_review_logs (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_id        BIGINT UNSIGNED NOT NULL,
  ai_analysis_id  BIGINT UNSIGNED NOT NULL,
  field_name      VARCHAR(32)     NOT NULL COMMENT 'priority/deadline/need_contact/risk_level/risk_reason/action',
  original_value  VARCHAR(500)    NULL     COMMENT 'AI 原值',
  new_value       VARCHAR(500)    NULL     COMMENT '人工修正值',
  reviewer        BIGINT UNSIGNED NOT NULL COMMENT '修正人',
  reviewed_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_ai_review_logs_order (order_id, reviewed_at),
  KEY idx_ai_review_logs_analysis (ai_analysis_id),
  CONSTRAINT fk_ai_review_logs_order FOREIGN KEY (order_id)
    REFERENCES orders (id) ON DELETE CASCADE,
  CONSTRAINT fk_ai_review_logs_analysis FOREIGN KEY (ai_analysis_id)
    REFERENCES ai_analyses (id) ON DELETE CASCADE,
  CONSTRAINT fk_ai_review_logs_reviewer FOREIGN KEY (reviewer)
    REFERENCES users (id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='AI结果人工修正记录';
```

> **一次修正产生 N 行**（改了几个字段就几行），而不是一行存 JSON diff。这样「哪个字段最常被 AI 判错」可以直接 `GROUP BY field_name` 统计出来——这是面试时很好讲的点：日志表设计要服务于未来的分析。

## 5. 枚举字典（应用层）

> 这些值在 Python 侧用 `str, Enum` 定义，**数据库不强制**，靠 Pydantic 校验。

### 5.1 订单状态 `orders.status`

| 值 | 含义 | 由谁写入 |
| --- | --- | --- |
| `IMPORTED` | 已导入，待分析 | 导入接口 |
| `ANALYZING` | AI 分析中 | AI Worker 取任务时 |
| `ANALYZED` | 分析完成 | AI Worker 写回 |
| `TASK_CREATED` | 已生成 RPA 任务 | 硬规则合并后 |
| `COMPLETED` | 任务成功 | RPA 回传成功 |
| `FAILED` | 任务最终失败 | 重试超限 |

### 5.2 任务状态 `tasks.status`

见《需求规格》第 9 章状态机。终态：`SUCCESS` / `FAILED` / `CANCELLED`。

### 5.3 优先级 `priority`（`tasks` 与 `ai_analyses` 共用）

`LOW` < `MEDIUM` < `HIGH`。取出队顺序按 `HIGH → MEDIUM → LOW`，同级按 `created_at` 升序（先来先做，避免饿死）。

### 5.4 风险等级 `risk_level`

`LOW` / `MEDIUM` / `HIGH`。命中《需求规格》§8.2 任一异常条件 → 至少 `MEDIUM`。

### 5.5 `deadline`

`TODAY` / `TOMORROW` / `NONE` / `YYYY-MM-DD`。用 `VARCHAR` 而非 `DATE`：前三个是**语义值**不是日期，混在 `DATE` 列里没法表达。

## 6. 索引设计说明

| 索引 | 服务的查询 |
| --- | --- |
| `uk_tasks_order` | 「一单一任务」约束 + 按订单查任务 |
| `idx_tasks_status_priority` | **claim 出队**（`WHERE status='QUEUED' ORDER BY priority, created_at`）与后台任务列表筛选 |
| `idx_orders_status` | 后台按状态筛订单 |
| `idx_orders_imported_at` | 后台按导入时间倒序分页 |
| `idx_ai_analyses_order` | 取某订单最新一次分析结果 |
| `idx_task_executions_task` | 任务详情页展示执行历史 |
| `idx_ai_review_logs_order` | 订单详情页展示修正历史 |
| `idx_tasks_status` + `heartbeat_at` | **僵尸任务回收**：`WHERE status='RUNNING' AND heartbeat_at < NOW() - INTERVAL 5 MINUTE` |

### 6.1 僵尸任务回收

RPA Worker 在 `RUNNING` 状态下崩溃，任务会永远卡住。解决办法：

1. Worker 每 30 秒调 `POST /rpa/tasks/{id}/heartbeat`，更新 `heartbeat_at`
2. 一个**定时任务**（每分钟跑一次）扫描：`status='RUNNING' AND heartbeat_at` 超过 5 分钟未更新
3. 判定为僵尸 → `retry_count + 1`，`status` 回到 `QUEUED` 重新入队（或超限则置 `FAILED`）
4. 当前那条 `task_executions` 记录置 `FAILED`，`error_code='WORKER_LOST'`

这是分布式任务系统绕不开的问题，也是**面试的高价值考点**：任务被领走后 Worker 挂了怎么办？不处理就是「任务卡死在 RUNNING」。

**刻意不加的索引**：`buyer_message`、`address` 等文本字段不做全文索引——v1 后台搜索只按订单号/客户名精确或前缀匹配，全文检索不是本项目的重点。

## 7. 模拟 ERP 的数据库

模拟 ERP 是**独立应用、独立库** `mock_erp`，与主库 `ai_rpa` 不共享任何表、不做外键关联。

理由：
- 现实中 ERP 是**外部系统**，它的数据不归本平台管
- 强制分离后，「RPA 只能通过界面操作 ERP」这条约束在数据层也是真的——主库看不到 ERP 的表

模拟 ERP 库的建表（简化版，仅供 RPA 操作）：

```sql
-- mock_erp 库
CREATE TABLE erp_users (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  username      VARCHAR(50)     NOT NULL,
  password_hash VARCHAR(255)    NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_erp_users_username (username)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE erp_orders (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  erp_order_no   VARCHAR(64)     NOT NULL,
  source_order_no VARCHAR(64)    NOT NULL COMMENT '对应主库 orders.order_no，用于对账',
  customer_name  VARCHAR(64)     NOT NULL,
  phone          VARCHAR(32)     NOT NULL,
  address        VARCHAR(512)    NOT NULL,
  product_name   VARCHAR(255)    NOT NULL,
  sku            VARCHAR(64)     NOT NULL,
  quantity       INT             NOT NULL DEFAULT 1,
  amount         DECIMAL(12,2)   NOT NULL,
  status         VARCHAR(20)     NOT NULL DEFAULT 'DRAFT' COMMENT 'DRAFT/PENDING_REVIEW/APPROVED',
  created_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_erp_orders_no (erp_order_no),
  UNIQUE KEY uk_erp_orders_source_no (source_order_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE erp_inventory (
  id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  sku       VARCHAR(64)     NOT NULL,
  quantity  INT             NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_erp_inventory_sku (sku)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> `erp_orders.source_order_no` 是**对账字段**：RPA 执行成功后可据此核对主库与 ERP 数据是否一致。主库**不做**这个外键——两个库不能有外键关系。
>
> 它对 ERP 自己是**唯一键**：同一来源订单号只能录入一次（《模拟ERP设计》§7.2）。
> 应用层查重是为了给出「该来源订单号已录入」这句人话，唯一索引才是防并发穿透的底线；
> 两者都有，缺哪一层都留一个洞。老库补索引见 `migrations/011_add_erp_orders_source_unique.sql`。

## 8. 种子数据

`database/seed/` 下提供：

| 文件 | 内容 |
| --- | --- |
| `scripts/seed_admin.py` | 1 个管理员（用户名/口令取自 `.env`）。**不是 .sql**：bcrypt 哈希算不出来，写死在 SQL 里等于把口令固化进版本库 |
| `02_erp_users.sql` | **空文件（占位）**。模拟 ERP 的操作账号在应用启动时自建（`mock/erp/app/seed.py`），用户名/口令取自 `.env`。**不是 .sql** 的理由同管理员：bcrypt 哈希必须运行时算 |

| `03_erp_inventory.sql` | 若干 SKU 库存，其中**故意留 1 个库存为 0**，用于触发「库存不足」异常 |
| `04_orders_sample.csv` | 样例订单 CSV，**刻意覆盖每种业务场景**（见下），应当**导入成功** |
| `04_orders_sample_invalid.csv` | 格式非法的样例订单，用来演示「整批失败 + 一次返回全部错误」 |

> `04_orders_sample.csv` 里没有「订单号重复」和「手机号非法」两种情况 ——
> 这两条一旦出现就会让**整批**失败（见《API接口设计》§6.3 的部分失败策略），
> 混在正常文件里会把另外 7 个场景一起拖下水，所以它们单独放在 invalid 文件里。
> 「订单号已存在」的分支不需要专门的数据：把 `04_orders_sample.csv` 再导一次就会触发。

### 8.1 样例订单必须覆盖的场景

设计样例数据时就要覆盖所有分支，否则跑不出完整的状态机：

| 场景 | 期望结果 |
| --- | --- |
| 普通订单，无留言 | `priority=MEDIUM`，直接入队 |
| 留言「孩子明天生日，希望今天发货」 | `priority=HIGH`，`deadline=TODAY` |
| 留言「不要发顺丰，请发中通」 | `risk_level=MEDIUM`，需人工审核 |
| 金额 12000 元 | 硬规则命中，强制人工审核 |
| 地址只填了「北京市」 | 地址不完整，`risk_level=HIGH` |
| SKU 对应库存为 0 | 库存不足，需人工审核 |
| 黑名单客户名下订单 | 直接异常 |
| 订单号与已存在的重复 | 导入失败，记入 `import_batches.error_detail` |
| 手机号格式非法 | 导入失败，记入 `import_batches.error_detail` |

> 上表前 7 条由 `04_orders_sample.csv` 覆盖（都能正常导入，异常在**下游**判定），
> 后 2 条由 `04_orders_sample_invalid.csv` 覆盖（导入这一步就拦下）。
>
> **黑名单样本客户**：`04_orders_sample.csv` 里的最后一行（手机号 `13800007777`）。
> v1 的黑名单硬编码在规则引擎里，按**手机号**匹配而不是姓名 ——
> 姓名会重名，手机号不会。待 Phase 5 实现规则引擎时对齐这个号码。
>
> **「地址过短」是硬规则不是导入规则**：见《需求规格》§8.1，
> 它的判定发生在 AI 分析阶段（`risk_level=HIGH`），所以「北京市」这行
> 必须能**正常导入**。导入阶段只校验「字段有没有填」，不校验「填得好不好」。

> **这一节是给未来的自己看的**：跑通闭环靠的是数据覆盖分支，不是功能多。样例数据不覆盖，状态机就有分支永远测不到。

## 9. 迁移与版本管理

```
database/
├── schema/                     # 一表一文件，编号即执行顺序（外键依赖序）
│   ├── 001_users.sql
│   ├── 002_import_batches.sql
│   ├── 003_orders.sql
│   ├── 004_ai_analyses.sql
│   ├── 005_tasks.sql
│   ├── 006_task_executions.sql
│   ├── 007_ai_review_logs.sql
│   ├── 008_notifications.sql
│   └── 009_mock_erp.sql        # 第 7 章，独立库 mock_erp
├── migrations/                 # 后续变更，按 010_/011_ 递增
└── seed/                       # 第 8 章种子数据
```

> **为什么一表一文件**：编号即外键依赖顺序，`for f in schema/*.sql` 顺序执行即可建库，
> 不需要在读 SQL 之前先做人脑拓扑排序。改动某张表时 diff 也只落在那一个文件里。

v1 用**手写 SQL 迁移**即可，不引入 Alembic。理由：表结构少且稳定，手写 SQL 更直观、更便于在面试时讲清楚每一张表为什么这么设计。Phase 8 如果表结构开始频繁变动，再考虑引入 Alembic。
