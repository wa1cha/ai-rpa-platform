# 压力测试（Phase 8）

> 配套文档：`README.md`、`docs/需求规格.md`、`docs/部署说明.md`
> 工具：`scripts/loadtest_import.py`（本轮唯一新增代码，**不改任何产品代码**）

---

## 1. 压测什么、为什么

《需求规格》§11 给 Phase 8 定的唯一硬指标是 **「模拟 100 单/分钟」**；
这条指标的**用意**在 §4.2 与 §12 写得很直白：

> 订单导入接口**不**同步调用 LLM。100 单/分钟下同步调用会直接阻塞导入。

也就是说，AI 分析之所以做成异步（导入 → AI 队列 → Worker 后台分析），
就是为了让**导入的响应时间与 LLM 的耗时解耦**。Phase 8 要用真流量把这件事量出来：

- 导入接口在 100 单/分钟下**始终是亚秒级响应**（因为它压根不碰 LLM）；
- 订单进 AI 队列堆积，由后台 Worker 按自己的节奏排空；
- 导入的响应时间**不随队列增长或 LLM 变慢而恶化**。

## 2. 方法

`scripts/loadtest_import.py` 是一条命令跑完的自管压测：

| 环节 | 做法 |
| --- | --- |
| 假 LLM | 脚本**进程内**起一个 OpenAI 兼容桩（stdlib `http.server`，**零新依赖**），`--stub-latency-ms` 模拟真实模型延迟 |
| 打桩 Worker | 脚本拉起一个 workers 子进程，用环境变量 `AI_BASE_URL` 把它的 LLM 调用指到桩上（pydantic-settings 里真环境变量优先于 `.env`） |
| 打流量 | 用 `mock/platform/generate_orders.py` 的生成器造 CSV，按 `--rate` / `--burst` 打 `POST /api/v1/orders/import`（管理员 JWT） |
| 采样 | 运行期每 3s 采一次 AI 队列深度（Redis `ZCARD`）与几个订单状态计数 |
| 排空 | 导入结束后等 AI 队列清空，记排空耗时与速率 |
| 报告 | JSON 落 `backend/var/loadtest_report_<时间>.json`（`var/` 已 gitignore） |

**数据隔离**：压测订单一律 `LT` 前缀，与演示用的 7 单区分；脚本结束时打印按前缀清库的 SQL。
**不花钱**：AI 侧走假 LLM，不产生任何 API 费用。

## 3. 实测结果（2026-10-03，本机）

环境：macOS 单机；MySQL / Redis 为本机 brew；主平台 `127.0.0.1:8000`（bare-metal）；
Docker Compose 栈压测期间**已停**；打桩 Worker 并发 5（与线上默认 `AI_WORKER_CONCURRENCY=5` 一致）；
假 LLM 延迟 1500ms（贴近真实模型量级）。

### 3.1 稳态 100 单/分钟（规格口径）

```bash
<PYTHON_BIN> scripts/loadtest_import.py --total 300 --rate 100
```

| 指标 | 值 |
| --- | --- |
| 导入成功 | **300 / 300**（失败 0，6 个批次，每批 50 单） |
| 导入耗时 | 150.06 s（≈ 120 单/分钟；因首批在 t=0 发出，实测略高于目标值） |
| 导入延迟 | p50 **48.4 ms** · p95 **57.3 ms** · p99 57.3 ms · max 57.3 ms |
| AI 队列峰值 | **57** 条 |
| 排空 | 从 50 条起，**19.0 s** 清空（157.5 单/分钟） |
| 假 LLM 命中 | 307 次 |

队列是**锯齿形**：每 30 s 到一批 50 单 → 队列冲到 ~50 → Worker 在 ~19 s 内排空 → 回到 0。
导入延迟全程稳定在 **~50 ms**，与队列涨落、与 1.5 s 的 LLM 延迟毫无关系。

| t(s) | ai_queue | IMPORTED | TASK_CREATED |
| --- | --- | --- | --- |
| 0.0 | 0 | 7 | 0 |
| 12.1 | 25 | 32 | 20 |
| 60.7 | 57 | 57 | 100 |
| 85.0 | 0 | 0 | 157 |
| 145.7 | 0 | 0 | 257 |
| 167.0 | 10 | 10 | 292 |

### 3.2 突发 300 单（最能说明解耦的一组）

```bash
<PYTHON_BIN> scripts/loadtest_import.py --total 300 --burst
```

| 指标 | 值 |
| --- | --- |
| 导入成功 | **300 / 300**（失败 0，6 个批次几乎同时发出） |
| 导入耗时 | **0.07 s** |
| 导入延迟 | p50 **44.5 ms** · p95 **46.0 ms** · p99 46.0 ms · max 46.0 ms |
| AI 队列峰值 | **300** 条（全部堆积） |
| 排空 | 从 300 条起，**99.3 s** 清空（181.3 单/分钟） |

队列从 300 **线性**下降到 0（~3.1 单/秒 = 恒定吞吐）：

| t(s) | ai_queue | TASK_CREATED |
| --- | --- | --- |
| 6.1 | 295 | 0 |
| 30.4 | 215 | 80 |
| 60.7 | 122 | 180 |
| 91.1 | 22 | 280 |
| 97.2 | 2 | 300 |

**关键对比：导入 300 单只花 0.07 s，AI 分析这 300 单要 99.3 s。**
两条路径的时间差三个数量级 —— 这正是异步解耦要达成的效果。若导入同步调 LLM，
这笔 300 单的导入接口要扛 300 × 1.5 s ≈ 450 s，直接不可用。

## 4. 瓶颈分析

| 环节 | 实测 | 说明 |
| --- | --- | --- |
| **导入** | p95 < 60 ms，与负载无关 | **不是瓶颈**。同步路径只做校验 + 逐行 INSERT + 一次 `ZADD` 入队，不碰 LLM |
| **AI 分析** | 排空 ~181 单/分钟 | 天花板 ≈ `AI_WORKER_CONCURRENCY / 单次 LLM 延迟` = 5 / 1.5 s ≈ **200 单/分钟**；实测 181 已接近理论值（差额是每单的 CAS + 写库开销）。分析队列停在这个数上时，`ANALYZING` 状态恒为 5（= 并发数） |
| **RPA 执行** | 未纳入本轮 | 单 Worker 串行 + `MOCK_ERP_PAGE_DELAY_MS=1500`，是**已知硬瓶颈**；规格 §13 明确 v1 不做多 Worker 并发 |
| **导入 INSERT** | 未改动 | `order_repository.add_all` 是逐行 INSERT（代码里已标注的非最优实现）。本轮**只测不改**；在 100 单/分钟量级下它够快，不是当期瓶颈 |

结论：**在规格口径 100 单/分钟下，导入侧有数量级余量，AI 侧并发是主要可调项，
RPA 侧是设计上就认下的上限。**

## 5. 复现

前置：本机 MySQL / Redis 在跑、`init_db.sh` 跑过、主平台已起（`./scripts/start.sh`）、
没有别的 workers 在跑（脚本会检查 `logs/workers.pid`）、dev 库为演示前基线
（7 单 `IMPORTED`）。

```bash
# 先小跑冒烟，确认自管管线通（桩起得来、Worker 认到桩、导入成功、队列涨落）
<PYTHON_BIN> scripts/loadtest_import.py --total 30 --rate 100 --drain-timeout 60

# 规格口径：100 单/分钟，300 单
<PYTHON_BIN> scripts/loadtest_import.py --total 300 --rate 100 --out backend/var/loadtest_report_paced.json

# 突发模式：一口气全发，看队列堆积与线性排空
<PYTHON_BIN> scripts/loadtest_import.py --total 300 --burst --out backend/var/loadtest_report_burst.json
```

跑完按脚本末尾打印的 SQL 清库回基线（见 §7）。

## 6. 诚实局限

- **桩延迟 ≠ 真 LLM**：真实模型耗时波动大、偶发 429/超时，本压测把 AI 侧简化成固定延迟 + 必然成功。
  它能证明「导入不被 LLM 阻塞」这条**结构性**结论，但不能替代真调模型时的稳定性/费用评估。
- **补偿任务会顺手捞起既有演示单**：假 LLM 命中 **307** 次而非 300 —— 多的 7 次是
  `ai_reconciler` 的 L1 腿把库里 7 条既有 `IMPORTED` 演示单（超过入队宽限期）重新入队分析了。
  这是产品**预期行为**（导入后入队失败/漏入队的补偿），不是压测脚本的误差。压测套件把
  这 7 条一并算进了队列峰值与排空，量级上可忽略。
- **单机**：压测进程、主平台、Worker、MySQL、Redis 全在同一台机器上抢 CPU，绝对数字偏保守。
- **未含 RPA 全链路**：只覆盖「导入 + AI 队列解耦」；RPA 执行阶段（含 mock ERP）的吞吐与
  稳定性不在本轮范围（规格 §13 已认下单 Worker 串行）。
- 本轮创建的任务会停在 `task_queue`（压测没起 RPA Worker），属预期。

## 7. 清理压测数据

压测订单以 `LT` 前缀隔离。`orders` 删除会**级联**清 tasks / task_executions /
ai_analyses / ai_review_logs；`notifications.related_task_id` 无外键，需显式删：

```sql
DELETE n FROM notifications n JOIN tasks t ON n.related_task_id = t.id
  JOIN orders o ON t.order_id = o.id WHERE o.order_no LIKE 'LT%';
DELETE FROM orders WHERE order_no LIKE 'LT%';
DELETE FROM import_batches WHERE filename LIKE 'loadtest%';
```

再清两个队列键，并把 7 条演示单退回 `IMPORTED`（即《部署说明》§8 的演示前基线）：

```bash
redis-cli -n 0 DEL ai_rpa:ai_queue ai_rpa:task_queue
# §8 全量重置见 docs/部署说明.md
```
